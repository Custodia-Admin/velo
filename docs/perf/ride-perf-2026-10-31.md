## Read this first: the absolute numbers are contaminated

During every run the laptop was shared with two other jobs:

- another agent's local pytest integration gates (4–5 processes at ~90 % CPU,
  1 h 20 min+);
- another agent's Chrome rendering a Velo ride on :4180, which took ~41 % of
  the iGPU render engine (measured from `/proc/<pid>/fdinfo` with
  `scripts/gpu-busy.py`).

Load average was 12–17 and the CPU package ran at 82 °C, held at ~2.1–2.8 GHz
out of a 4.5 GHz maximum. **Bare Cesium**
(`scripts/perf-bare.html`: same Cesium build, terrain, imagery and photoreal
mesh, but none of Velo's scene) only reached:

| bare Cesium, 1920×1080        | fps (3 samples across the session) |
|-------------------------------|------------------------------------|
| empty globe                   | 18.5 – 31.6                        |
| World Terrain + Bing imagery  | 18.2 – 22.0                        |
| + Google photoreal 3D tiles   | 4.7 – 7.9                          |

An empty Cesium globe runs at 60 fps on this GPU when the machine is idle. So
every number below has a ceiling of roughly 8 fps with photoreal tiles. **The

So the remaining cost on the iGPU is **distributed GPU fill/draw**: the globe
pass, entity and ground-primitive draws and clouds each contribute a similar
slice, and no single knob gets to 45 fps. The photoreal mesh only dominates
when run at quality knobs (8–15 fps bare); the governor's degradation is what
lifts the ride to ~20. Next levers, in order of the table: fold the road
corridor/shadow into fewer ground primitives, cheaper entity rendering
(primitives instead of entities where possible), cloud layer off on Balanced,
and a lower pixel budget (resScale ≤0.7) on the iGPU.

## Which knob contributed most

Each item below has its own measurement:

1. **The GPU ground pick (`scene.sampleHeight`) was the biggest Velo-side
   cost.** Over the photoreal mesh, the avatar's ground sampler rendered a
   pick pass and read it back synchronously. A 30 s window had 624–1,242
   `readPixels` calls and 166–231 `sampleHeight` calls. `readPixels` alone
   was **29 % of main-thread self time** (CPU profile). Each call stalls until
   the GPU finishes the frame: **35–270 ms per call** against
   **~3 ms for `Cesium3DTileset.getHeight`** (CPU intersection with the
   rendered tiles; `scripts/` probe). After the switch there are 0
   `sampleHeight` calls and 2 `readPixels` calls per window, and main-thread
   script time dropped from 86 % to 49–60 %. This one change produced most of
   the gain between the `ab` and `ab2` rounds.
2. **The 3D tiles themselves**, which Velo can only throttle. Blocking both
   ion 3D assets (photoreal 2275207 + OSM buildings 96188) took the after1
   build from 2.2 to 8.6 fps; blocking either one alone gave about 3.5 fps.
   Bare Cesium shows the same thing (photoreal 7.9 fps vs terrain + imagery
   22 fps). To reduce it: photoreal SSE 16 → 24 plus skip-LOD / foveated /
   cache budget, and globe SSE per tier.
3. **Avatar entities rebuilt every frame.** Each procedural cyclist part was
   an Entity with a time-varying position, so Cesium re-created its geometry
   (and shaders) every frame. Profiles before the fix showed the dominant
   cost in geometry rebuild plus GroundPrimitive re-tessellation of the
   clamped shadow ellipse. These are now static Primitives moved by
   `modelMatrix`, with a single disc Primitive for the shadow.
4. **Two opaque Bing base layers.** The Viewer default and `setupBaseImagery`
   stacked two copies, so every imagery tile was fetched, decoded, uploaded
   and sampled twice. `baseLayer: false` now always.
5. **Resolution scale / MSAA / shadows / fog / atmosphere**: no measurable
   effect within the noise of the contended bisect (`scripts/perf-bisect.py`;
   the same baseline varied 2× between its first and last row). On an idle
   machine, the bisect with assets blocked showed the globe as the largest
   render cost (hiding it: 12 → 39 fps). Tiers now carry a resolution scale
   and a pixel budget (balanced = 0.85, ≤1920×1080 rendered pixels), and the
   tier is picked from the GPU until the rider chooses one: Arc / Iris / Apple
   / phone GPUs → Balanced, discrete → High, software → Low.
6. **Paused and finished rides render on demand** (`scene.requestRenderMode`).
   Nothing moves, so the iGPU idles instead of redrawing the same frame at
   60 Hz. Multiplayer keeps continuous frames.
7. **HUD route widgets** (elevation profile, minimap) re-rendered Recharts /
   SVG 60 times a second. They now update on quantised distance.

## Would the stutter remain on an RTX-class GPU?

**Measured, no longer inference:** card t_0bf516d2 (PR #17) A/B'd the ride on
cat-bed's RTX 5090 — vsync-locked 60 fps at 1080p after the governor landed.
The original reasoning is kept below.

- The remaining cost is GPU-bound drawing of the photoreal mesh plus Cesium's
  globe/atmosphere passes. A discrete GPU (RTX 4090/5090 class) has roughly
  10–20× the Arc iGPU's fill and geometry throughput and its own memory, and
  Google 3D tiles in Cesium routinely hold 60 fps there.
- The synchronous pick stall scaled with GPU frame time, so a fast GPU hid
  most of it. It is removed now anyway.
- What remains on any GPU is **main-thread tile work while streaming**: glTF
  parse, Draco/texture decode handoff, `texImage2D` uploads, and the 3D-tiles
  traversal. That causes hitches when the camera moves fast into new tiles,
  not sustained low fps. Pixel streaming from cat-bed's RTX 5090 would remove
  both the GPU limit and the client's tile work, at the cost of an encode /
  network / decode latency budget. Velo's per-frame CPU work is now small
  enough that a local discrete GPU would also be fine.

## Tooling (for v2)

- `?perf=1` → `PerfOverlay`: fps, mean / p95 frame time, % of frames over
  33.8 ms, globe + 3D tile queue, canvas size × resolution scale, dpr, MSAA,
  tier, on-demand flag. `window.__veloPerf()` returns the same object.
- `scripts/perf-ride.py`: Home → scenic route → Demo ride. Measures
  startup / steady windows, longtasks, main-thread %, heap, `readPixels` /
  `sampleHeight` counts, and an optional CPU profile.
- `scripts/perf-ab.sh` + `scripts/perf-ab-summary.py`: interleaved
  before/after runs.
- `scripts/perf-bare.py` + `perf-bare.html`: a bare-Cesium ceiling for
  calibrating the harness and machine.
- `scripts/perf-bisect.py`, `perf-probe.py`, `perf-trace.py`,
  `perf-pause.py`, `perf-calibrate.py`, `cpuprofile-tree.py`, `gpu-busy.py`.
- `scripts/camera-shots.py`, `scripts/settings-shots.py`: framing shots of
  every camera mode at 1440 and 390, and the distance picker.
